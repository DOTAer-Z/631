# 故障诊断平台 —— 部署说明 v2（PostgreSQL 单库 / Docker 镜像版）

> 本文档替代旧版《部署.docx》。最大变化：**数据库由 MySQL + MongoDB 统一为单一 PostgreSQL**
> （日志原文/窗口等文档数据由 PostgreSQL 的 JSONB 兼容层承载），部署组件更少、更易移植。
> 更新时间：2026-06-06

---

## 一、项目总体说明

基于日志的嵌入式/软件系统故障诊断平台：前端展示 + 后端分析服务，把每个测试用例（`Test_***`）
的故障轮/正常轮日志解析入库、做时间窗口分析，并在网页端按 run / 故障类型 / 故障·正常状态查询展示。

```
用户 → 前端(nginx, :8080) → 后端(FastAPI, :5000) → PostgreSQL（结构化数据 + JSONB 日志文档）
                                                   └ embedding/LLM：当前关闭，可后接（见第七节）
```

### 与旧架构的对应关系

| 旧架构 | 现架构 |
|---|---|
| MySQL（结构化数据） | PostgreSQL 表（fault_types / cases / runs / …） |
| MongoDB（log_entries / log_windows / 上传等） | PostgreSQL `mongo_docs` JSONB 表（pymongo 兼容层 `app/mongo_compat.py`） |
| FAISS 向量库 + 本地 embedding 模型 | 当前镜像未内置（精简）；需要时按第七节启用 |
| 知识图谱(kg) | 同上，按需启用 |

---

## 二、部署架构（组件）

| 组件 | 镜像 | 端口 | 说明 |
|---|---|---|---|
| frontend | `faultdiag-frontend:latest` | `8080:80` | Vue + nginx，UI；`/api` 反代到后端 |
| backend | `faultdiag-backend:latest` | `5000:8000` | FastAPI；启动自动建表/seed/导入数据集 |
| postgres | `postgres:16` | 容器内 5432（默认不对外） | 主库，数据持久化在命名卷 `pgdata` |

- 后端镜像**已内置数据集（79 个 Test）**，首次启动自动初始化并导入，开箱即用。
- 镜像为**精简版**：不含 torch/faiss/sentence-transformers（embedding/向量检索，默认关闭）。

访问地址：

| 服务 | 地址 |
|---|---|
| 前端 | `http://<host>:8080/` |
| Swagger API 文档 | `http://<host>:5000/api/docs` |
| 健康检查 | `http://<host>:5000/health` |

## 三、配置体系

三层配置（与旧版一致的思想）：

1. `backend/app/config.py` — 配置项与默认值
2. 运行时环境变量 — 由 docker-compose 注入（见 `deploy/docker-compose.prod.yaml` 与 `deploy/.env`）
3. 关键变量：

| 变量 | 默认 | 说明 |
|---|---|---|
| `POSTGRES_HOST/PORT/USER/PASSWORD/DB` | postgres/5432/postgres/secret/fault_diagnosis | 主库连接 |
| `ENABLE_EMBEDDING` | False | 本地 embedding/向量检索开关 |
| `ENABLE_LLM` | False | 大模型诊断开关 |
| `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL` | （见 config.py） | 启用 LLM 时填写 |
| `AUTO_INGEST` | 1 | 容器启动是否自动导入内置数据集 |

> 正式环境务必在 `deploy/.env` 改强密码：`cp deploy/.env.example deploy/.env` 后修改 `POSTGRES_PASSWORD`。

## 四、部署方式一：本机 Docker 一键启动（构建并运行）

适合开发机/第一次构建镜像。

```bash
cd <项目根>/deploy
cp .env.example .env            # 可选，改密码
docker compose -f docker-compose.prod.yaml up -d --build
```

等待后端自检完成（约 1 分钟，含建表 + 导入 79 个 Test）：

```bash
docker compose -f docker-compose.prod.yaml ps           # backend 状态应为 healthy
docker compose -f docker-compose.prod.yaml logs -f backend   # 看到 “[ingest] 完成：cases=79 …”
```

验证：

```bash
curl http://localhost:5000/health                       # {"status":"ok"}
curl http://localhost:5000/api/v1/overview              # dataset: cases 79 / runs 158 / fault 79 / normal 79
# 浏览器打开 http://localhost:8080/  → 系统概况 / 数据处理→日志列表
```

停止 / 重置：

```bash
docker compose -f docker-compose.prod.yaml down          # 停止（保留数据卷）
docker compose -f docker-compose.prod.yaml down -v        # 停止并清空数据库卷（下次启动重新初始化）
```

## 五、部署方式二：另一台电脑（离线 save / load，最快）★推荐用于换机测试

不需要源码、不需要联网拉依赖，只搬三个镜像。

### 5.1 在已构建好的机器上导出

```bash
cd <项目根>/deploy
sh save-images.sh                 # 生成 faultdiag-images.tar.gz（约 300MB）
```

把这两样拷到目标机（U盘/scp 均可）：
- `faultdiag-images.tar.gz`
- `deploy/` 目录（至少需要 `docker-compose.prod.yaml`、`.env.example`、`load-images.sh`）

### 5.2 在目标机加载并启动

```bash
cd deploy
sh load-images.sh faultdiag-images.tar.gz     # docker load 三个镜像
cp .env.example .env                          # 可选改密码
docker compose -f docker-compose.prod.yaml up -d   # 注意：不要 --build，直接用加载的镜像
```

> 目标机只需装好 Docker（含 compose 插件）。数据集已在镜像内，启动即自动分析，无需另拷数据。

## 六、部署方式三：服务器级部署

### 6.1 直接用 compose（最简单，推荐中小规模）

与第五节相同：`load-images.sh` → `docker compose up -d`。配合 `restart: unless-stopped`，宿主重启后自动拉起。
如需对外，开放安全组/防火墙的 `8080`（前端）即可；`5000` 可只在内网/调试用。

### 6.2 推私有镜像仓库 + K8s（沿用旧版 docx 流程，仅镜像名/数量变化）

镜像由旧版“前端+后端+MySQL+Mongo”简化为“**前端 + 后端 + postgres**”。变量与推送：

```bash
NS=faultdiagnosis
REGISTRY=easzlab.io.local:5000
TAG=release-2026-06-06

# 打 tag
docker tag faultdiag-backend:latest  $REGISTRY/faultdiag-backend:$TAG
docker tag faultdiag-frontend:latest $REGISTRY/faultdiag-frontend:$TAG
# postgres 用官方 postgres:16，或一并推私有仓库

docker login $REGISTRY
docker push $REGISTRY/faultdiag-backend:$TAG
docker push $REGISTRY/faultdiag-frontend:$TAG
```

K8s 侧（与旧版相同的 apply / rollout / status 流程）需要把 Deployment 改为：
- 删除 mysql、mongo 两个 Deployment 及其 PVC；
- 新增/保留一个 **postgres** Deployment + PVC（数据卷挂 `/var/lib/postgresql/data`）；
- backend 注入 `POSTGRES_*` 环境变量指向 postgres Service；
- 数据初始化：可保留镜像入口自动初始化（首个副本执行），或改为一次性 Job 跑 `create_tables.py + seed.py + ingest_dataset.py`，backend 仅 `uvicorn` 启动（多副本时更稳妥）。

> 旧 docx 的 `frontend-deployment.yaml / backend-deployment.yaml` 的 image 替换、`kubectl apply`、
> `rollout restart/status`、`get pods` 等命令照旧，只是把镜像名换成上面的 `faultdiag-*`。

## 七、部署后：手动上传新数据并分析

镜像内置的是初始 79 个 Test。要分析**新数据**，把包含若干 `Test_***/` 子目录的文件夹拷进后端容器再跑导入脚本即可（脚本幂等，复用既有解析/窗口逻辑）：

```bash
# 1) 在后端容器内建一个接收目录
docker compose -f docker-compose.prod.yaml exec backend mkdir -p /app/incoming

# 2) 把宿主机上的新数据（目录里是 Test_xxxx 子文件夹）拷进去
docker cp ./我的新数据/Test_60001 faultdiag-backend:/app/incoming/Test_60001
#   （多个就多拷几次，或直接拷整个目录：docker cp ./我的新数据/. faultdiag-backend:/app/incoming/）

# 3) 导入并分析
docker compose -f docker-compose.prod.yaml exec backend python ingest_dataset.py --data-root /app/incoming

# 4) 刷新前端「数据处理 → 日志列表」即可看到新 run；首页概览统计同步更新
```

补充：
- 只想重导某个用例：`... ingest_dataset.py --only Test_60001`（默认数据根为镜像内置 `/app/data`）。
- 想让新数据**永久内置**进镜像：把数据放进项目 `data/` 后重建后端镜像（第四/五节的 build）。
- 每个 `Test_***` 会按 `fault_events.log` 自动判定 round_1=故障轮 / round_2=正常轮，解析出
  故障类型、错误事件、日志窗口；正常轮 0 报错作为对照。

## 八、后续启用 LLM / Embedding（两条路，按需）

当前精简镜像默认关闭这两项。要启用：

**路线 A：把能力加回后端镜像（改代码/依赖后重建）**
1. 在 `backend/requirements.prod.txt` 加回 `faiss-cpu`、`sentence-transformers`（embedding/向量检索）；LLM 仅用 `openai` 客户端，镜像已含。
2. 重建后端镜像（第四节 build）。
3. 在 `deploy/.env` 设 `ENABLE_LLM=True` / `ENABLE_EMBEDDING=True`，并填 `LLM_API_KEY`、本地模型路径/向量库路径（可用卷挂载 `outputs/vector_store`、模型目录）。

**路线 B：外部服务集成（不改本镜像）**
- 把 LLM/embedding 做成独立容器（如自建 OpenAI 兼容服务 / embedding 服务），加进同一个 compose；
- 后端置 `ENABLE_LLM=True`、`LLM_BASE_URL=http://<你的服务>/v1`、`LLM_API_KEY=...` 指向它即可。

> 两条路都已为之留好开关（`ENABLE_*`、`LLM_BASE_URL/API_KEY/MODEL`，见 `app/config.py`），核心查询/分析功能不受影响。

## 九、运维速查

```bash
# 看状态 / 日志
docker compose -f docker-compose.prod.yaml ps
docker compose -f docker-compose.prod.yaml logs -f backend

# 重启某个服务
docker compose -f docker-compose.prod.yaml restart backend

# 改了密码后重建数据库（会清空数据，重新初始化）
docker compose -f docker-compose.prod.yaml down -v && docker compose -f docker-compose.prod.yaml up -d

# 进后端容器排查
docker compose -f docker-compose.prod.yaml exec backend sh

# 直接连库
docker compose -f docker-compose.prod.yaml exec postgres psql -U postgres -d fault_diagnosis -c "\dt"
```

镜像清单：

| 镜像 | 体积(约) | 用途 |
|---|---|---|
| `faultdiag-backend:latest` | ~770MB | FastAPI 后端 + 内置数据集 + 自初始化 |
| `faultdiag-frontend:latest` | ~97MB | 前端静态站 + nginx 反代 |
| `postgres:16` | ~640MB | 主库 |
| 离线分发包 `faultdiag-images.tar.gz` | ~300MB(gz) | 三镜像合一，`load-images.sh` 加载 |

## 十、国内服务器构建加速（可选）

若在国内自行 `--build` 较慢，可在 `backend/Dockerfile` 顶部改用镜像源：
- base 改 `docker.m.daocloud.io/library/python:3.11-slim`
- pip 加 `-i https://pypi.tuna.tsinghua.edu.cn/simple`
- 前端 `frontend/Dockerfile` 已使用 `registry.npmmirror.com`

推荐优先用第五节的 **save/load 离线包**，免去目标机重复构建。
